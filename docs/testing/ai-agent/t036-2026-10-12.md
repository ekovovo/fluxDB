## 交付内容

### 1. 协议解析与校验（纯函数，`crates/fluxdb-app/src/parts/ai_decision_provider.rs`）
- `parse_systemone_answers`：只接受 `type=choice` / `type=score`。
  - Choice：`choice` 必须在候选集合内（模型编造的 ID 拒绝）；`probabilities` 每个值必须是
    有限数且在 0–1；`confidence` 存在时同样必须在 0–1。
  - Score：`score` 必须是有限数；`confidence` 同上。
  - `noul`/bool 等其它类型在本 Provider 用途下明确判为协议不匹配（不猜语义）。
  - 缺失 `confidence`/`usage` 保留 `None`，**不伪造 0**。
- `finite_number`：拒绝字符串数字与 NaN/Inf。
- `parse_systemone_usage`：`{input_tokens, output_tokens}` 均缺失时不报 usage（由计量层记 `unknown`）。

### 2. 传输与取消/超时（`DecisionTransport` + `UreqDecisionTransport`）
- 生产走 ureq：**不跟随重定向**（避免认证头被 302 引到非预期主机）、受控 `timeout_global`、
  响应体 256 KiB 上限。
- 请求前与应用到达后各检查一次 `CancelFlag`：取消路径**不发请求、不解密凭据**。
- 错误只映射为固定中文原因（HTTP 状态 / 超时 / 网络失败 / 协议不匹配），**不透出响应正文、URL、凭据**。

### 3. Provider（`SystemOneDecisionProvider`，实现 `core::DecisionProvider`）
- 统一 `DecisionRequest`：单 `decision` Choice 问题，`criteria` 键即候选 ID。
- 凭据通过 `DecisionCredentialLease` **在请求前才申请**一次性明文；认证头在作用域结束即丢弃；
  `TransportAuth`/`SystemOneDecisionProvider` 的 Debug 均脱敏。
- `decision_provider_from_storage`：只接受 `api_protocol=system-one` 且用途为 decision 的模型；
  不按模型名猜协议，也不把生成协议冒充成决策协议。构造时复用 **T033 候选过滤**
  （全局出站闸门 → 停用 → 用途 → 单模型出站许可 → 凭据），再校验 System One 协议。

### 4. 用量记账（`MeteredDecisionProvider`）
- 每次决策请求在 `ai_usage_ledger` 登记一条 `purpose=decision`，占用会话并发名额；
  有 usage → `actual`，缺 usage → `unknown`（不伪造 token）。复用与主模型相同的账本边界。

### 5. core DTO 扩展
- `DecisionResponse` 增加 `confidence: Option<f64>` 与 `usage: Option<Usage>`，只承载 Provider 明确返回的事实。

## R02 真实模型验收结果（2026-10-12）

用户本机已有合格 Jev 决策模型（`#models` 显示：用途「决策」、`Decisions · inception/mercury-decide:free`、
凭据「已配置」、允许出站）。执行：

```sh
FLUXDB_AI_DECISION_MODEL='决策模型' \

```

实测（脱敏）：

```
决策模型: id=model-8ef4cc86-... display=决策模型 model=inception/mercury-decide:free protocol=system-one revision=4
endpoint=Some("https://openrouter.ai/api/alpha/decisions") full_url=true
decision ok: chosen=Some("候选A") confidence=Some(0.042496694638422365) usage=Some(Usage { input_tokens: 99, output_tokens: 1, cached_input_tokens: 0 }) elapsed_ms=1978
```

- **Choice 解析正确**：返回的 `choice` 落在候选集合内（候选A），概率/置信度为合法 0–1。
- **usage 上报正确**：input 99 / output 1 tokens。
- **凭据不出宿主**：脚本只输出模型 ID/协议/revision、chosen/confidence/usage/耗时，无 Key、无响应正文。

### 验收中发现并修复的真实缺陷：DNS/IPv6 解析挂起
- 首次调用（默认解析器）稳定超时；改用连接测试同款 **IPv4 优先解析器**后立即成功。
  系统 DNS 返回的不可用 IPv6 地址会让默认解析器在真实决策模型上挂起。
- 修复：`UreqDecisionTransport` 复用 `crate::ai_agent`（禁重定向 + `PrefersIpv4Resolver`），与设置页「测试连接」一致。

### 默认 deadline 上调（用户决定，2026-10-12）

- 设计 §18 起始参数 deadline 为 **800ms**，实测远程决策模型往返约 2s，800ms 必然超时。
  按用户决定**上调为 3000ms**：`DECISION_DEADLINE_MS = 3_000`（无自动重试；熔断与「不每轮等待」仍归 T037）。
- **同口径上调普通 chat 模型**：`MODEL_RESPONSE_DEADLINE_MS = 3_000`，作用于「等模型开始响应」
  （DNS/连接/响应头）阶段，**不是**整段请求的 `timeout_global`。
  - 这是有意的分阶段口径：若把 `timeout_global` 设成 3s，任何超过 3s 的流式回答都会被拦腰截断。
  - `read_timeout` 仍为 60s（对话侧 30s），长回答不受 3s 影响。
  - 新增 `TransportLimits::response_deadline` 字段与回归用例
    `transport_response_deadline_is_separate_from_long_read_budget`。
- **顺带修复 chat 路径同款 DNS 缺陷**：此前 `stream_chat` 用默认解析器，与决策 Provider 同病；
  现统一走 `chat_agent()`（IPv4 优先 + 禁重定向），与设置页「测试连接」一致。

### 3000ms 对该远程模型的实测仍偏紧（如实记录）

对用户本机 Jev 模型连续 4 次测量（`FLUXDB_AI_DECISION_TIMEOUT_MS=30000`，排除客户端截断）：

| 次 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| elapsed_ms | 7154 | 2358 | 4047 | 2556 |

- 4 次均**返回正确结果**（`chosen=候选A`，usage 99–102 input / 1 output），协议解析稳定。
- 波动很大（约 2.4s–7.2s），**3000ms 会间歇性超时**（实测用 3000ms 默认跑时即出现一次超时）。
- 这是远程 `:free` 模型的端到端时延，不是协议问题；按设计 §18，Jev 超时应走「放弃建议、使用基础策略」。
- 是否再上调（如 8s）或改用更快的决策模型 / 自建 endpoint，属 **T037** 的熔断与默认模型策略，本轮不擅自改。
