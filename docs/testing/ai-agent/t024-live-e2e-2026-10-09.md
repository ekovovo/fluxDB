## 真实场景

通过模型：已有 `Zhipu GLM` / `glm-5.3-flash` / `openai-responses`。

| 步骤 | PostgreSQL 实际结果 | MySQL 实际结果 |
| --- | --- | --- |
| 初始状态 | `1|pending`、`2|paid` | 同左 |
| 真实模型读取 | `db.query=succeeded`，真实两行回执，正文准确总结 | 同左 |
| 首次写计划 | `db.execute=waiting_approval`，没有执行回执，数据不变 | 同左，使用参数绑定 |
| 拒绝审批 | 数据不变，数据库 AFTER UPDATE 触发器计数 0 | 同左 |
| 重新生成 | 新写调用/审批仍未执行，触发器计数 0 | 同左，参数数组非空 |
| 批准恢复 | `succeeded`，真实 `affected_rows=1` | 同左 |
| 后端回读 | 精确等于 `1|paid`、`2|paid`，触发器计数 1 | 同左 |
| 模型后续行为 | 自主 `db.query` 回查 id=1，正文确认回执与行值一致 | 正文复述写回执；独立测试回读核对，不宣称模型自主回查 |
| 重复恢复 | 触发器计数仍为 1，没有第二次数据库写入 | 同左 |
| 清理 | schema 不存在，`pg_namespace` 计数 0 | 数据库不存在，`information_schema.schemata` 计数 0 |

触发器计数来自真实数据库，不以本地工具事实行数代替副作用次数。
最终日志：`target/t024-e2e/logs/pg-zhipu.log`、`mysql-zhipu.log`。

## 失败与受阻记录

1. 公司自建模型最小冒烟返回“就绪”，但 PostgreSQL 读取回合重复提交相同查询；两次真实读取成功后，被第三次重复调用保护暂停为 `waiting_user`，没有最终正文。**该模型完整闭环未通过**，日志 `pg-company-stalled.log`。
2. Zhipu MySQL 初次较自由的参数化写请求达到生产 1024 token 输出上限，正文/工具调用缺失，Turn 为 `completed` 且有长度上限 notice。保留 `mysql-zhipu-length-limit.log`；简短、明确 SQL/参数的提示重跑后通过，不抹去首次失败。
3. 可见桌面实例使用独立 `FLUXDB_PROFILE=t024-e2e-1009`、配置副本、PG 固定测试目标、1200×800/light 启动；工具无法连接 native 服务，**无实际 UI 输入/发送/批准/拒绝，无截图、暗色或窄窗视觉结论**。
4. GPUI Headless 只证明进程内交互，不宣称系统窗口、IME、AX 映射、主题观感或真实桌面事件通过。
