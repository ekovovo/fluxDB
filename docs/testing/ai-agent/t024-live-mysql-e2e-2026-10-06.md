# A：真实模型 + 真实 MySQL 端到端（2026-10-06，macOS / podman）

## 环境

- 数据库：podman `unit-mysql`（mysql:8.0.34，`127.0.0.1:38831`，应用连接 id=2 `docker`）。
- 模型：`Zhipu GLM`（`openai-responses`）；隔离：配置库复制到 `/private/tmp/fluxdb-live-mysql` 后使用。
- 测试数据只写专用库 `fluxdb_ai_smoke`，结束 `DROP DATABASE IF EXISTS`。
- 凭据走宿主解密路径，未外显。

## 执行

`FLUXDB_AI_LIVE=1 FLUXDB_AI_LIVE_ROOT=/private/tmp/fluxdb-live-mysql FLUXDB_AI_LIVE_MODEL='Zhipu GLM' \
 FLUXDB_AI_LIVE_MYSQL_CONNECTION=2 cargo run -p fluxdb-app --example ai_live_mysql_e2e`
（生产链路：`prepare_ai_conversation` → `run_ai_conversation_turn` → `DecideApproval` → `prepare_ai_resume_job` → `run_ai_conversation_resume_approval`）

## 结果

| 步骤 | 实际 |
|---|---|
| ① fixture | `CREATE DATABASE fluxdb_ai_smoke` + `orders(id,status,amount)` + 2 行；写入前 `["1|pending","2|paid"]` |
| ② 读回合 | `db.query` **succeeded**，真实回执 `rows=[["1","pending"],["2","paid"]]`；模型复述准确 |
| ③ 写回合 | 模型用 **`db.execute` + `parameters`（`?` 占位符）** → 停在审批（`waiting_approval`、无回执），审批前数据未变 |
| ④ 批准 + 恢复 | `db.execute` **succeeded**，回执 **`affected_rows=1`** |
| ⑤ 后端核对 | `["1|paid","2|paid"]`（写入真实生效） |
| ⑥ 清理 | `DROP DATABASE fluxdb_ai_smoke` |

⇒ 真实模型 + 真实 MySQL：读取 → 审批 → **参数化写入**一次 全部通过（同时验证了 B 的 MySQL 绑定能被模型用起来）。

## 本轮修的产品缺口

**工具 schema 没告诉模型 `parameters` 的 tagged 格式**：第一次写回合模型发了缺 `type` 的参数，
被应用层按设计拒绝（`invalid_parameters: parameters[0] 缺少 type`）。
已按主设计 §20.2 把 `$defs.parameter`（null/bool/i64/u64/f64/decimal/text/bytes 八种 tag）与
`items: {$ref}` 补进 `db.query`/`db.execute` 的输入 schema（`ai_sql_policy.rs`，改用 `r##"…"##`
避免 JSON 里的 `"#` 提前终止原始字符串），模型随后即用对了格式。

## 发现的新问题（未修，待跟进）

- 模型在写入成功后想"再读回验证"，发出的读请求带 `?` 占位符但**未带 parameters**，
  MySQL 驱动返回协议级错误 `1835 (HY000): Malformed communication packet`（`execution_failed`）。
  写结果本身已独立核对成功，但这个错误信息对模型不可行动。
  建议：在 `ai_sql_exec` 里做一次"SQL 含占位符但 parameters 为空"的前置校验，
  返回 `placeholders_without_parameters` 之类的可操作错误（同样的检查对 PG `$n` 适用）。
