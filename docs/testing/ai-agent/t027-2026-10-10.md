# T027 结果句柄、分页与保留管理验收（2026-10-10）

平台：macOS arm64。全部测试使用隔离临时目录 / 独立 SQLite，不读生产配置与凭据、不联网、无付费请求。

## 交付

- **ResultRef + 分页快照**：`crates/fluxdb-app/src/parts/ai_tool_registry.rs` 的 `ResultStore` 按 session/turn 绑定归属，`read_page` 返回行数与字节双上限的有界页 + 续读游标。
- **大结果不进上下文**：`SqlExecutionOutcome::to_model_json` 只把 `RECEIPT_SAMPLE_ROWS`（5 行）样本写进回执，完整行走仓库；回执带 `row_count`/`rows_omitted`/`result_ref`。
- **result.read_page 工具**：新增 `crates/fluxdb-app/src/parts/ai_result_pages.rs`，只读已取得的快照切片，不重连数据库、不重跑来源工具。
- **spill 与保留**：`ResultStore::put` 超出内存预算的部分写受控根 `ai-results/results/<uuid>.json`；`SpillFact`（产出工具/相对路径/文件字节数/内容哈希）随回执登记到 `ai_results`，`retention_kind='retained'`。仓库内存预算 `RESULT_STORE_MEMORY_BYTES`（32 KiB）**独立于**工具层回执上限 `SQL_RESULT_MAX_BYTES`（128 KiB）。
- **重启过期与清理**：`recovery::recover_on_startup` 过期全部 `memory` 结果，并按 TTL 过期 `retained`（无 TTL 的不因重启失效）；SQLite 事务只改状态，过期落点经 `RecoverySummary::retained_paths_to_purge` 交回应用层，在受控根下删文件（路径越界的落点直接丢弃），删除失败只记日志、不阻断恢复扫描。

## 端到端（真实 SQLite + 生产链路）

`crates/fluxdb-app/tests/ai_result_paging_e2e.rs` 的 `wide_query_spills_to_retained_row_and_is_readable_page_by_page`：
用**真实 SQLite 文件与真实驱动**（demo MockConnector 固定只返回 2 行，触发不了 spill），

1. **大结果不进上下文**：200 行宽行查询，工具层 128 KiB 上限截断到 141 行，回执只带 5 行样本，
   `rows_omitted=136` 属实，回执体积 < 32 KiB。
2. **retained 落点可核对**：`ai_results` 行 `retention_kind='retained'`，带受控根内相对路径、
   内容哈希、字节数；拼回根目录就是真实 spill 文件；回执与结果卡都不含宿主绝对路径。
3. **`result.read_page` 分页读回**：按 32 行/页读完 141 行，id 不重不漏、确实分了多页，
   `total_items` 与 `row_count` 一致。
4. **跨会话读不到**：另一 turn 的 `ResultStore` 读本轮句柄报 `unknown_result`。
5. **重启语义**：走生产 `RecoverOnStartup`，retained 仍 `available`、spill 文件未被删。

## 过程中修复的真实缺陷

0. **端到端暴露的装配缺陷**：`run_ai_conversation_turn` 原先靠调用方另传一份结果仓库给回执登记，
   而工具目录里已经持有同一个仓库——两处各传一次，`ai_conversation_tools` 等直接调
   `run_ai_conversation_turn` 的路径就会漏传，溢写结果被登记成 `memory`、重启后文件变孤儿。
   改为 `ToolCatalog::with_results` 让目录持有仓库并经 `catalog.results()` 读回，删掉重复传参。
1. `read_page` 原先只返回内存部分并给出「还有更多」游标，spill 条目永远读不到（模型会以为读完却少数据）；改为按需从受控文件回读，文件缺失/损坏/条目数不符 → `result_damaged`（不返回假空页）。
2. `standard_sql_catalog_with_results` 注册了 `result.read_page` 实现却没有把它的 spec 加进目录，`ToolCatalog` 拒绝注册（`工具 result.read_page 没有对应的 ToolSpec`）；补上 spec。
3. `ai_results` 的 `retention_kind` 固定写 `'memory'`，溢写文件重启后没有归属，清理无从下手；`insert_result` 改为接收 `ResultRetention`，并校验相对路径不得越界。

5. **spill 在生产里不可达**：仓库内存预算原本复用 `SQL_RESULT_MAX_BYTES`，与工具层回执上限是同一个值；
   工具投影已被截断到 128 KiB，仓库必然装得下，`put` 永远走不到溢写分支，
   于是 `ai_results` 一律登记成 `memory`、`relative_path` 永远为空，spill / retained 成了死代码。
   新增独立常量 `RESULT_STORE_MEMORY_BYTES = 32 * 1024`，并加回归断言
   `result_store_budget_is_below_tool_projection_cap` 锁住「预算必须小于回执上限」。
6. **retained 行字节数取错口径**：`byte_count` 原先写的是回执 JSON 长度，
   而 retained 行描述的是受控文件——清理与配额会按回执长度算，和真实磁盘占用对不上
   （实测 65621 vs 文件 98784）。`ResultRetention::Retained` 增加 `byte_count` 字段，
   对 retained 行改用 spill 文件实际大小。
7. **翻页调用认领来源的 spill 文件**：`result.read_page` 的回执回显来源句柄（`result-1`），
   回执登记又按该 id 查 `SpillFact`，于是每个翻页调用都被登记成「又一条 retained 结果」
   并复用来源的 spill 文件（同 turn 内多个 `result.read_page` 行 `relative_path` 完全相同）。
   `SpillFact` 增加 `tool_id`，`spill_retention` 只在「句柄产出工具 == 本次调用工具」时才认领；
   翻页现在按 `memory` 登记（回归断言见 `ai_result_pages_recorded_rows_match_the_store_spill_facts`）。
