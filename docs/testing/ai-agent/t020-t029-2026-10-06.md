# T020/T029 进展记录（2026-10-06，macOS）——**未完成，不勾选**

## 范围与版本

- 分支 `agent`；设计入口：`docs/ai-agent-design.md` §25（审批/授权）、§29（停止/重启/未知副作用）、§31（面板）。

## 改动要点

**loop**
- `LoopEvent::ApprovalRequired` 现在携带 `call`（provider_call_id/tool_id/arguments）与 `tool_version`，
  这样宿主才可能落盘"待审批的工具调用"，并在批准后按同一参数恢复执行。

**storage**
- `sessions::create_tool_call(..., status)`：支持以 `waiting_approval` 建事实行（原 `start_tool_call` 保留为 `running` 的封装）。
- `sessions::load_tool_call` / `list_tool_calls_for_turn`：恢复与断言用；`ToolCallView` 增加 `receipt_json`。
- `sessions::find_assistant_message_for_turn`：审批决定等迟到事件挂回同一条助手消息（不新建消息）。
- `conversation::checkpoint`：等待审批/等待用户**不再被标记为 error**（保持 pending，UI 才能区分暂停与失败）。

**app**
- `run_ai_conversation_turn` 收到 `ApprovalRequired` 时写：`ai_tool_calls(waiting_approval)` + `ai_approvals(pending)` +
  一个 `notice` 片段（payload 含 `approval_id`/`plan_hash`/`approval_revision`）；Turn 状态 `waiting_approval`。
  只有真的产生待审批项才是 `waiting_approval`，达到迭代上限等属于 `waiting_user`。
- `AiConversationCommand::DecideApproval{approval_id,approved,expected_revision}`：对象级 CAS；
  拒绝时写 `denied` 事实 + 可见片段（永不执行）。
- `AppController::prepare_ai_resume_job(approval_id)`：重建同一会话/轮次/助手消息的 job。
- `run_ai_conversation_resume_approval(...)`：`Approved` + `find_valid_approval(plan_hash)` 双重复核（fail closed）→
  重新 `prepare` 参数 → 执行一次 → 写真实回执 → 把回执作为 tool 消息交回模型继续（续写而不是清空已有正文）。

**desktop**
- `decide_ai_chat_approval(...)`：提交决定；批准后启动恢复任务。
- 面板审批卡：`notice` 片段带 `approval_id` 且 pending 时渲染「批准执行 / 拒绝」按钮（debug selector `ai-approve:<id>` / `ai-deny:<id>`），
  并提示"批准后仍会复核 plan_hash"。

## 子 Agent 测试与修复

### 子 Agent A（`crates/fluxdb-app/tests/ai_conversation_approval_guard.rs`，6 例，全过）

| # | 场景 | 结果 |
|---|---|---|
| 1 | CAS 冲突（stale revision 重复提交） | 通过（状态与 revision 不变、未执行） |
| 2 | 未批准直接 resume | 通过（fail closed、无回执、`call_count=0`） |
| 3 | 批准后 plan_hash 漂移 | 通过（拒绝执行） |
| 4 | 批准后 invalidate | 通过（拒绝执行） |
| 5 | 拒绝路径 | 通过（`denied`、无回执、无法再开） |
| 6 | 批准后重复 resume | **首轮失败**，修复后通过 |

**修复的 P1（子 Agent 发现）**：恢复入口只校验审批与 `find_valid_approval`，**没有消费批准**，也没有检查
`ai_tool_calls.status` / `receipt_json`，因此重复 resume 会**真实二次执行**工具（对写工具＝重复副作用），
且第二次 `insert_result` 撞唯一约束的错误被 `tracing::warn!` 吞掉、账面看不出。
已修：resume 前要求 `status='waiting_approval'` 且 `receipt_json IS NULL`，并在同一事务里把调用推进到 `running`、
把批准置为已消费（`invalidated` + reason `consumed`）后才执行；重复 resume 直接 fail closed。

### 子 Agent B（`apps/fluxdb-desktop/src/main_parts/ai/tests.rs`，5 例，全过）

`cargo test -p fluxdb-desktop --offline ai_` → **36 passed**（新增 5 + 既有 31，无回归）。
覆盖：pending 审批卡渲染出 `ai-approve:<id>`/`ai-deny:<id>`、点击批准真实落库（pending→approved, rev 1→2）、
已决定/非 pending 不显示按钮、普通文本与工具卡渲染不回归。全部经生产 Load → AppState → 渲染快照 → 实际控件。

**修复的 P2（子 Agent 发现）**：决定后原审批片段仍停在 pending，面板会继续显示可点的批准/拒绝按钮。
已修：决定时就地更新原片段（同 id）为 `complete` 并写入 `decision`（approve/deny 都写），面板据此隐藏按钮。
