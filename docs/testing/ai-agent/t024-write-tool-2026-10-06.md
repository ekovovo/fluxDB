## 实现要点

- **注册写工具**：`standard_sql_catalog(resolver, include_write)`；桌面按**本轮固定目标连接**决定是否注册：
  连接被标记只读 → 连 `db.execute` 的 spec 都不暴露；否则暴露，但 `authorize` 对 `ToolRisk::Write` 强制 `RequireApproval`。
- **写权限来源**：`connection_is_read_only(config)`（SQLite endpoint 标记或 `options["read_only"]=="true"`）+
  `kernel_policy_for_connection(config)`：读允许、写=连接未标只读、管理默认拒绝；**没有固定连接时写为 false**。
  顺带修复 `connection_store`：行级 `read_only` 现在对非 SQLite（TCP）连接也往返保留（此前只在 SQLite endpoint 上生效）。
- **工具作用域收窄**：resolver 只装本轮固定目标连接 → 模型不能借 `conn:<其它 id>` 访问别的连接（越权目标返回 `connection_not_found`）。
- **Plan/审批链路**：`claim_ai_approved_call` 在执行前重算 plan hash 并复核 Agent 权限、审计、工具版本、固定目标；
  同连接存在未核实 `unknown` 副作用时拒绝冲突写入（真实窗口已复现该守卫生效）。
- **拒绝也要有事实**：内核 Deny（权限/白名单/审计）不经过 `ToolStarted`，现在会补 `ai_tool_calls(status=denied)` 事实行 + 可见结果卡，
  且不登记结果句柄（拒绝不是执行结果）。
- **回执落盘失败不再吞掉**：工具已执行但回执写失败时，把调用标为 `unknown` 并把错误显式交给用户（此前只 `warn` 后继续，
  调用会停在 `running` 与事实不符）。
- **恢复提示同步**：重启横幅在调用真正执行/拒绝后同步更新文案，不再停留在"尚未执行"。

## 本轮修复的真实缺陷

1. **`plan_hash` 依赖 JSON 键顺序（P1）**：`serde_json` 的 `Map` 顺序受 `preserve_order` 特性影响，
   同一语义参数在不同编译单元（app 库 vs 桌面/夹具）会算出**不同 hash**，跨进程按 plan_hash 复核必然误判失效。
   已把规范化放进 `plan_hash` 内部：`canonical_json_str` 递归按字典序排序对象键、数组保持顺序、非 JSON 原样。
   测试：`plan_hash_is_order_independent_and_canonical`（顺序无关 + 语义变化必换 hash + 非 JSON 不 panic）。
2. **回执行 ID 解析过于乐观**：回执保存原先假设行 ID 一定是 `{turn}-toolcall-{provider_call_id}`，
   命中不了就新建，撞 `UNIQUE(turn_id, iteration, source_ordinal)`。现在按
   ID → `(turn_id, provider_call_id)` → 取下一个空闲序号 的次序解析（新增 `find_tool_call_id_by_provider_call` / `next_tool_call_ordinal`）。
