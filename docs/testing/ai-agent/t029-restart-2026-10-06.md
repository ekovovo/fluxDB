## 实现要点

- **storage**：`ai_platform/recovery.rs::recover_on_startup`（SQLite `IMMEDIATE` 短事务，失败整批回滚）；
  工具事实行 API 机械拆到 `ai_platform/tool_calls.rs`（`sessions` 保留 re-export，行为不变）；
  `conversation::upsert_event_part_in_transaction` 供"审批决定 + 原卡片"同事务更新。
- **app**：`AiConversationCommand::RecoverOnStartup` → `parts/ai_recovery.rs`；恢复执行 `claim_ai_approved_call` 在另一短事务内复核
  当前 Agent 权限/审计、规范化参数、工具版本、固定目标、plan hash，再把 `waiting_approval` 占用为 `running` 并消费批准，事务外才执行。
- **desktop**：首帧在 `navicat_main/render.rs` 把恢复排进 AI IO 串行队列（只执行一次）；失败保留错误并禁用发送；
  恢复提示用 `recovery_status` 渲染（未知=红色 Alert，其余=黄色 Alert）；未知工具卡显示"结果未知"。
- 规则：专用只读工具（`db.query`/`db.search_objects`/`db.explain`）的 `running` 记为**读取中断**（call=`cancelled`，不伪造回执）；
  写/未知工具的 `running` 记 `unknown` + Turn `outcome_unknown`；`prepared` 只表示未执行；已有终态成功回执不改写；
  历史 `approved` 退回 `pending`（`reason_code=restart_reapproval`，revision+1，旧 UI CAS 失效）；过期批准不可用；同连接存在未核实未知副作用时拒绝冲突写入。

### 主 Agent 按子 Agent 发现修复的问题

1. **P1 部分提交**：审批已改为 `approved` 后卡片写入失败会留下不一致（且未知/终态仍会被批准）。
   → 决定改为"先校验非终态待审批调用，再单事务 CAS + 原卡片更新"，失败整批回滚（子 Agent A 补充的批准/拒绝故障注入均验证回滚）。
2. 启动扫描查询用错列（`created_at_ms`/`updated_at_ms` 不存在）→ 改 `started_at_ms`/`finished_at_ms`。
3. 启动失败反馈被后续 `Load` 清空、且会把历史会话塞进 AppState → 恢复只扫描并保留错误，面板自行 `Load`。
4. 未知写工具卡被扫成"已停止"（读中断的措辞）→ 增加 `execution_status`，UI 显示"结果未知"（红色）。
5. 决定后原审批卡仍是 pending、按钮可重复点 → 就地更新为 `complete` + `decision`。
6. 重启后拒绝仍显示"等待批准"提示 → 拒绝时同步更新恢复提示为"已被你拒绝，没有执行"。
7. GPUI 测试偶发 `async-io` 非确定性 abort：`show_message` 的计时器改用 `cx.background_executor().timer`（跟随 GPUI executor）。
